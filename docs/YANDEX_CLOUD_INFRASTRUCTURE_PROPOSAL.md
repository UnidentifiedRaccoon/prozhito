# «Прожито»: предложение по инфраструктуре Yandex Cloud

Дата исследования и уточнения: **31 августа 2026 года**. Статус: **в отдельном каталоге `prozhito` развёрнут DB-backed пилот; завершаются приёмочные проверки**. [Решение 39](DECISIONS.md#открытый-сайт-39) уточняет решения 37/38: сайт полностью открытый, без регистрации, аккаунтов и прогресса читателей. Вход есть только в отдельной редакторской админке. Нагрузка — около 100 посетителей в день, месячного денежного лимита нет, запуск БД в 07:45 МСК и ночное окно 00:00–08:00 сохраняются. Фактические ресурсы — [pilot.json](../infra/yandex-cloud/pilot.json), результаты — [packet](../harness/tasks/2026-08-31-yandex-cloud-pilot-implementation.md).

## 1. Рекомендация в одном абзаце

React / TypeScript / Vite остаётся читательским клиентом; отдельная статическая админка и один модульный backend TypeScript / Fastify работают через **Serverless Containers**. Контент, редакции и только редакторские учётные записи — в **Managed PostgreSQL**, изображения — в **Object Storage**. HTTPS и маршрутизация — **API Gateway**, собственные домены — **Certificate Manager**, секреты — **Lockbox**. Первый пилот развёртывается проверяемыми скриптами и CLI; Terraform и GitHub OIDC / Actions остаются отдельным незавершённым пунктом автоматизации, не выдаются за уже настроенные. На запуске методист редактирует и публикует материалы, читатель открывает сайт без входа. Kubernetes, отдельные микросервисы, Redis и постоянно работающие прикладные ВМ сейчас не нужны.

«Оптимально» здесь означает минимальную эксплуатационную нагрузку, близость к уже знакомому FinPulse и возможность развивать продукт без смены базы. Это не минимально возможный счёт за облако любой ценой. Владелец указал веб-пилот примерно на 100 пользователей в день и отказался от месячного денежного лимита на этом этапе. Рабочее предположение: 1–3 методиста, преимущественно текст и изображения, без видео, платежей и круглосуточных договорных обязательств.

## 3. Отличия предлагаемой схемы от референса

| FinPulse | Предлагается для «Прожито» | Зачем |
|---|---|---|
| Fastify отдаёт и API, и Vite-сборку | Статические сборки в Object Storage; backend обслуживает API | Не расходовать контейнерные вызовы на изображения и клиентские файлы |
| Админка Next.js в отдельном контейнере | Отдельная Vite / React-админка | Сохранить отдельный интерфейс без второго серверного приложения |
| JSONB с номером редакции и прямым обновлением runtime-контента | Черновик, проверка, публикация неизменяемой редакции, история | Не показывать незавершённые правки читателям |
| PostgreSQL запускается по двухчасовой аренде | Тестовая БД запускается и останавливается по суточному расписанию; переход на 24/7 — позднее | Доступность предсказуема, ручной запуск и публичный start URL не нужны |
| БД с публичным IP; VPC другого проекта | Собственная VPC; БД без публичного IP | Изолировать доступ и жизненный цикл проектов |
| Schema bootstrap и seed при запуске | Отдельные версионированные миграции; однократный контролируемый импорт | Деплой не должен менять редакторский контент |
| Один admin из переменных окружения | Именные редакторские аккаунты и роли | Отзыв доступа, журнал авторства и отсутствие общего пароля |

**Не использовать существующую БД FinPulse для production «Прожито».** Отдельная database внутри того же кластера разделяет имена и права, но не остановки, резервное копирование, нагрузку и отказ. С учётом действующей автоостановки экономия создаст прямую эксплуатационную зависимость. Ресурсы FinPulse остаются без изменений.

## 4. Целевая схема первого рабочего запуска

Условные имена доменов ниже не означают, что домен уже выбран или зарегистрирован.

```text
Читатель → app.<домен> → API Gateway reader
                        ├─ сайт и изображения → Object Storage
                        └─ /api/v1/content/* → backend Fastify

Методист → admin.<домен> → API Gateway admin
                          ├─ интерфейс → Object Storage admin
                          └─ /api/admin/* → тот же backend Fastify

backend → частная VPC → Managed PostgreSQL
        → Object Storage: загрузки и служебные экспорты
        ← Lockbox: секреты через сервисный аккаунт

GitHub Actions → WIF → Registry / выпуск статических сборок
                         → новая ревизия backend после проверок
```

Один backend содержит content, editorial access и publishing. Reader-шлюз открывает только GET content и status; маршрутов авторизации читателя или admin API в нём нет. Два шлюза сохраняют один origin для UI и API каждого приложения, позволяют раздельные правила доступа и не требуют отдельного балансировщика. Развитие пользовательских операций требует нового решения владельца.

| Компонент | Начальная конфигурация / ответственность |
|---|---|
| Yandex Cloud folders | Для первого пилота создан один отдельный `prozhito` (`b1gr37s9qf8nh0fuq1js`) в облаке `b1gmnnjgdcc1b7qhjmlk`; второй постоянно работающий контур сейчас не создаётся |
| VPC | Отдельная сеть на окружение; подсети во всех требуемых сервисом зонах, собственные группы безопасности |
| Managed PostgreSQL | Для теста один хост, 10 GiB network SSD, без публичного IP, ночная остановка. Расчётная база — `s3-c2-m8`, 2 vCPU / 8 GiB; меньший `c3-c2-m4` — кандидат после проверки доступности и стоимости. PostgreSQL 17 как кандидат, конкретная поддерживаемая версия фиксируется после проверки совместимости |
| Backend container | Стартовая гипотеза: 1 vCPU / 512 MiB, concurrency 8, timeout 30 s, без постоянно подготовленных экземпляров; параметры подтвердить нагрузочным тестом |
| Object Storage | Раздельные бакеты/права для reader-сборки, admin-сборки, опубликованных медиа и закрытых загрузок/экспортов; standard storage |
| API Gateway | Два шлюза; явные маршруты и методы. Reader-шлюз не проксирует admin API. Только шлюзы имеют право вызывать runtime-контейнер |
| Certificate Manager и DNS | В облаке найдена публичная зона `ncfg.ru.`; возможны свободные поддомены проекта с отдельными сертификатами после проверки DNS. Существующие записи не менять. Технический HTTPS-адрес API Gateway допустим; статический IP не требуется для serverless-схемы |
| Container Registry | Собственный registry или явно изолированные repositories; образы по digest / commit, очистка старых с сохранением rollback-версий |
| Lockbox / IAM | Раздельные секреты окружений; отдельные runtime, deploy, migrator и gateway identities с минимальными правами |
| Наблюдаемость | Cloud Logging, Monitoring и уведомления; инфраструктурный аудит, редакторский audit log в БД; это не аналитика поведения читателя |
| Суточное расписание | Закрытая Cloud Function управления только новой БД, таймеры запуска/остановки и периодическая сверка желаемого состояния. Публичного запуска платных ресурсов нет |

Статические бакеты могут быть закрыты от прямого анонимного доступа: шлюз читает объекты своим сервисным аккаунтом. API Gateway поддерживает интеграции с [Object Storage](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/object-storage) и [Serverless Containers](https://yandex.cloud/ru/docs/api-gateway/concepts/extensions/containers), а собственные домены — с [Certificate Manager](https://yandex.cloud/ru/docs/api-gateway/concepts/).

VPC не делает HTTP-адрес контейнера приватным: анонимный вызов технического URL необходимо запретить IAM. Авторизацию методиста дополнительно проверяет backend; наличие второго домена само по себе ничего не защищает. Для доступа к БД учесть служебные адреса Serverless `198.19.0.0/16`, а не только собственные подсети. Официальная документация требует подсети во всех зонах и предупреждает об увеличении холодного старта при подключении VPC. [Сетевая модель](https://yandex.cloud/ru/docs/serverless-containers/concepts/networking).

**До production выполнить короткую техническую проверку:** gateway → container → закрытая БД с проверкой TLS-сертификата и CA; получение секретов; cookies / CSRF через оба домена; доступный тип БД и зоны. Передача Lockbox-секретов в контейнер поддерживается, но на странице Serverless отмечена **Preview**. Это отдельный риск для согласования; fallback не должен молча превращаться в секрет в репозитории или обычном Terraform state. [Передача секретов](https://yandex.cloud/ru/docs/serverless-containers/operations/lockbox-secret-transmit).

## 5. Контент и редакторский процесс

Предлагаемый процесс:

1. Методист открывает Section и создаёт черновик от опубликованной редакции.
2. Меняет текст истории, девять полей разбора, разрешённые вопросы/пояснения и медиа. Произвольную структуру программы менять нельзя.
3. Предпросмотр использует те же компоненты и контракт, что reader, но доступен только редактору.
4. Сервер проверяет структуру, ссылки, media metadata, область редакционного исключения и номер исходной редакции. Содержательное/safety-одобрение остаётся отдельной человеческой ролью, а не автоматическим обещанием правильности.
5. Кнопка «Опубликовать» атомарно переключает указатель на проверенную неизменяемую редакцию. Сохранение черновика не публикует его.
6. Журнал фиксирует автора, время, основание и опубликованную редакцию. Конфликт одновременного редактирования возвращает 409, не затирает чужую работу.
7. Откат возвращает прежнюю опубликованную редакцию без удаления истории.

В PostgreSQL хранить идентификаторы, порядок и связи отдельно от структурированного JSONB-содержимого Section. JSONB — формат хранения документа, не разрешение принимать произвольные поля. Сущности для детального проектирования: программа/уровни, Section, неизменяемые редакции, черновики, публикации, ссылки на медиа, редакторские аккаунты/сессии/роли, журнал. Точные таблицы и миграции — следующий этап, не часть этого плана.

В документ Section входят полный story Markdown, девять стабильных ключей разбора, редакторские метаданные, ссылки на изображения с alt/crop, а для разрешённых трёх Section — вопросы и пояснения. Правила поведения и дизайн остаются кодом. Методические паспорта, источники и внутренние 48 действий не выдаются публичным API. Изображения не хранятся base64 в JSONB. Общий текст обеих визуальных версий не раздваивается в два независимых канона.

Публичный API отдаёт только опубликованное. Ответы маркируются revision / ETag; при открытии Section клиент закрепляет одну редакцию для истории и решения, чтобы публикация посреди чтения не смешала тексты. Для межсекционных изменений нужен единый publication manifest со ссылками на редакции. Если backend/БД недоступны, клиент показывает понятное состояние повторной загрузки, а не незаметно подмешивает старые встроенные данные.

Начать с runtime-чтения опубликованного контента через API. Публичные JSON-снимки в Object Storage можно добавить позже, если потребуется сохранять чтение при отказе БД; это отдельный publisher с контролем атомарности и восстановления, а не обязательная усложняющая часть первого запуска. CDN также добавлять по измеренным задержкам и трафику.

### Переход от Markdown к редакторской БД

- До одобрения и cutover канон остаётся в репозитории.
- Сначала определить полноту импорта: 22 Section, 27 существующих вопросов, адресные пояснения, иллюстрации, focal points, источники и методические паспорта.
- Сделать проверяемый импорт на staging: совпадение текстов, ID, порядка, границ, девяти звеньев и области упражнений; полный QA представления.
- При cutover зафиксировать источник истины: предлагается БД для редакторского и опубликованного контента; Markdown и книга становятся воспроизводимым экспортом этой редакции. Методические правила и продуктовые решения остаются в Git.
- Не поддерживать два независимых процесса правок Git ↔ БД. Изменение истории должно синхронно отражаться в экспорте книги и Section; скрытого архивного ответвления не создавать.
- Импорт только однократный, с проверкой пустого target и явным подтверждением. Старт контейнера и deployment никогда не запускают повторный seed production-контента.

Решение 37 фиксирует направление тестовой инфраструктуры, но не сам перенос источника истины. Cutover требует отдельной принятой записи в DECISIONS и синхронизации PRODUCT / AGENTS / harness после проверенного импорта.

## 6. Доступ, эксплуатация и безопасность

- Именные редакторские аккаунты, роли `editor`, `publisher`, `owner`; в малой команде одному человеку можно назначить несколько ролей. Методисту не нужны доступ к облачной консоли или пароль БД.
- Для browser-админки — отзываемые server-side сессии, HttpOnly / Secure / SameSite cookies, host-only cookie, CSRF-защита и проверка Origin для изменений. Пароли только как стойкие hashes; MFA/SSO для админов — в критерии допуска перед внешним запуском, конкретный способ выбрать при согласовании доступа.
- Ограничить попытки входа и частоту записи. Защита не должна полагаться только на память одного serverless-экземпляра; использовать общий счётчик или управляемое правило на входе. Регистрация читателей сейчас отсутствует.
- Раздельные роли PostgreSQL: runtime без DDL, migrator с ограниченными правами схемы, отдельные credentials по окружениям. Read replicas и отдельная БД для каждого модуля пока не нужны.
- Ограничить максимальное число экземпляров и пул соединений: стартовая гипотеза pool 3–5 на экземпляр; общий предел считать по всем возможным зонам, одновременно живущим ревизиям и migration runner с запасом для обслуживания. Не использовать неограниченное масштабирование относительно `max_connections`.
- Загружать файлы по короткоживущим разрешениям в закрытую upload-зону Object Storage, проверять тип/размер до публикации. Не пропускать большие файлы через backend: у обычного HTTP-ответа контейнера лимит 3,5 MB. Не выполнять фоновые задачи после ответа в request-driven контейнере. [Лимиты](https://yandex.cloud/ru/docs/serverless-containers/concepts/limits).
- Markdown без исполняемого HTML; запрет опасных URL и проверка загружаемых файлов. Секреты, cookies, пароли, персональные данные и полные тела редакторских запросов не попадают в logs.
- Автоматические бэкапы с PITR; предлагаемый retention 14 дней и закрытый экспорт опубликованного контента после публикации. На старте провести восстановление в отдельный cluster и проверить тексты; наличие настройки backup не равно проверенному восстановлению. Настраиваемый стандартный retention сервиса — 7–60 дней. [Резервные копии](https://yandex.cloud/ru/docs/managed-postgresql/concepts/backup).
- Предварительные цели пилота: восстановление последней публикации из отдельного экспорта; для черновиков целевой RPO до 15 минут, RTO до 4 часов. Это цели проверки, не гарантии Yandex Cloud; подтвердить восстановлением либо пересогласовать до cutover.
- Алерты: доступность API/БД, 5xx, задержка, ошибки публикации, CPU, соединения, диск 70/85%, возраст последнего успешного backup. Ожидаемую ночную остановку отличать от инцидента; не подавлять ошибки запуска утром, неостановленную ночью БД или устаревший backup. Настроить срок хранения логов, например 14 дней.
- По явному решению владельца месячный денежный лимит и связанные пороговые budget-уведомления сейчас не настраиваются. Ограничения масштабирования, срока хранения старых образов и контроль неожиданного трафика сохраняются: это техническая защита, не месячный лимит. Если бюджет будет добавлен позже, уведомления сами по себе **не останавливают расходы**. [Бюджеты](https://yandex.cloud/ru/docs/billing/concepts/budget).
- До хранения данных читателей отдельно согласовать их состав, доступ, удаление и применимые требования к обработке персональных данных. Само размещение в российском облаке не заменяет эту работу.

## 7. Доступность и стоимость

### Какой вариант выбирать

| Режим | База | Предварительный месячный бюджет | Ограничение |
|---|---|---:|---|
| Принятое направление теста | 1 хост, ночная остановка, дневная работа | **Около 5–7 тыс. ₽** | Предварительно на `s3-c2-m8`; ночное окно и отсутствие HA, размер полного резерва ещё уточняется |
| Редакторский пилот 24/7 — сравнение | 1 хост, постоянно работает | **7–9 тыс. ₽** | Нет HA и SLA однохостового кластера; сбой/обслуживание останавливает редакторский и content API |
| Первые внешние пользователи с требованием HA | 2 хоста в разных зонах | **13–16 тыс. ₽** | Выше устойчивость к отказу хоста; обновление версии БД всё ещё требует простоя |
| Повышенные требования к доступности | 3 хоста в трёх зонах | **19–23 тыс. ₽** | Дороже; не отменяет тестирование переключения и плановые окна |

Для теста владелец выбрал экономию и плановую ночную недоступность; однохостовый вариант остаётся без HA. Перед запуском с обязательной доступностью — минимум два хоста и пересмотр ночного расписания. Yandex Cloud не рекомендует один хост для высокой доступности; для двух и трёх хостов условия различаются. [Официальные ограничения HA](https://yandex.cloud/ru/docs/managed-postgresql/concepts/high-availability).

### Откуда взялась оценка

Это расчётный бюджет, **не выгрузка Billing и не коммерческое предложение**. Регион Россия, рубли с НДС, 720 часов, без грантов/CVoS, без постоянного staging, видео, платной рассылки, CDN/WAF, поддержки и регистрации домена. Предполагается до 1 млн gateway-запросов суммарно, 100 тыс. backend-вызовов, 1–5 GiB медиа, до 50 GiB внешнего трафика и небольшой объём логов. Просмотр страницы включает несколько HTTP-запросов; MAU нельзя напрямую подставлять вместо их количества.

- **Проверенная фиксированная составляющая:** в опубликованном тарифном примере `s3-c2-m8` CPU стоит 1,8792 ₽/vCPU·час, RAM — 0,5072 ₽/GiB·час. На один хост: `720 × (2 × 1,8792 + 8 × 0,5072) = 5 627,52 ₽` только за compute. На два — 11 255,04 ₽, на три — 16 882,56 ₽. SSD и превышение включённого объёма backup считаются дополнительно; HDD из примера сервиса к нашей SSD-конфигурации не подставлялся. [Тариф PostgreSQL](https://yandex.cloud/ru/docs/managed-postgresql/pricing).
- **Backend, пример, не замер:** 100 тыс. вызовов по 300 ms, 1 vCPU, 0,5 GiB дают около 63,21 ₽ до free tier и без холодных стартов/повторных запросов. Постоянно подготовленные экземпляры добавят плату за простой. [Тариф Serverless Containers](https://yandex.cloud/ru/docs/serverless-containers/pricing).
- **Шлюзы:** 1 млн суммарных вызовов — 142,30 ₽ до free tier; если доступен весь бесплатный объём 100 тыс., около 128,07 ₽. Не считать бесплатный объём заново на каждый из двух шлюзов. [Тариф API Gateway](https://yandex.cloud/ru/docs/api-gateway/pricing).
- Разница между посчитанным compute и верхнеуровневым бюджетом — **оценочный резерв**, а не подтверждённый тариф: SSD, backup, Object Storage и операции, трафик, Registry, Lockbox, логи, DNS и погрешность нагрузки. Точная построчная смета этих позиций нужна после выбора параметров в калькуляторе. [Тариф Object Storage](https://yandex.cloud/ru/docs/storage/pricing).

Free tier может уже использоваться другими проектами; скидки не гарантированы. Месяц в 31 день содержит 744 часа, что увеличит постоянный compute примерно на 3,3%. Постоянный staging добавит примерно ещё один однохостовый контур; поэтому для разработки достаточно локальной PostgreSQL, а staging поднимается для интеграционных проверок. Его запуск/остановка — только аутентифицированным оператором/CI, без публичного URL запуска платной БД.

### Уточнённая экономия по расписанию

При 16 часах работы в сутки получается 480 compute-часов за 30 дней: `480 × 7,816 = 3 751,68 ₽`, экономия compute — 33,3% относительно 24/7. Подтверждённый владельцем прогрев с 07:45 добавляет 7,5 часа в месяц: `487,5 × 7,816 = 3 810,30 ₽`, экономия — около 32,3%. Такой запас стоит около 58,62 ₽/месяц на выбранном классе. Время остановки, обслуживания, backup и аварийные задержки могут увеличить фактические часы.

Ориентир всего контура **около 5–7 тыс. ₽/месяц** получен уменьшением прежнего бюджета 7–9 тыс. ₽ приблизительно на 1,8 тыс. ₽ compute и округлением; это не точный потолок расходов. Диск, backup, хранилище сайта, шлюзы, логи и таймеры продолжают тарифицироваться. Для остановки с экономией используется `network-ssd`, а не `local-ssd`. [Правила остановки и оплаты](https://yandex.cloud/ru/docs/managed-postgresql/operations/cluster-stop).

### Минимальный класс: проверка вместо предположения

Read-only API 31 августа возвращает `b1.medium` / `b2.medium` (2 vCPU, 4 GiB), но официальная документация запрещает создание новых b1/b2/b3-кластеров. Нельзя брать их в смету только по присутствию в API. `c3-c2-m4` (2 vCPU, 4 GiB, диск от 10 GiB) также есть в ответе API и документации; для Intel Ice Lake Compute Optimized указано предоставление доступа по запросу. Доступность в выбранном облаке и конечная цена не подтверждены; 4 GiB сами по себе не доказывают меньшую стоимость. [Классы](https://yandex.cloud/ru/docs/managed-postgresql/concepts/instance-types), [ограничение платформы](https://yandex.cloud/en/docs/managed-postgresql/pricing).

Поэтому опорный вариант — расписание на доступном стандартном классе; перед созданием сравнить цену и доступность меньшего класса. Не заменять Managed PostgreSQL на самостоятельно обслуживаемую БД без отдельного решения.

## 7а. Ночное окно тестового контура

### Пользовательский контракт

Часовой пояс по рабочему контексту — **Europe/Moscow, МСК (UTC+3)**, независимо от настроек устройства. Каждый день:

- **08:00–00:00** — штатная работа reader и админки при готовой БД.
- **00:00–08:00** — глобальное состояние технических работ. Это не третий экран Section и не изменение контента.
- Текст: «Проводятся технические работы. Сайт доступен ежедневно с 08:00 до 00:00 по московскому времени».

Ночной экран и его минимальные стили входят в статическую сборку и доступны при остановленной БД. Публичный read-only status endpoint возвращает серверное время, режим, время следующего открытия и состояние готовности, не требует соединения с БД в ночном режиме. Backend должен уметь стартовать и отвечать на этот endpoint без успешной DB-инициализации. Таймеры браузера используются только для своевременного переключения UI; часы устройства не определяют право выполнять операции.

Frontend проверяет режим до загрузки контента и повторяет проверку при возвращении вкладки/на границе окна. Backend независимо отклоняет content/admin-операции в maintenance до обращения к repositories: `503`, код `scheduled_maintenance`, `Retry-After` до следующего открытия и `Cache-Control: no-store`. Ночной status не обращается к БД; статические файлы не блокируются. Уже скачанный контент невозможно отозвать у клиента — это эксплуатационный режим, не DRM.

В 08:00 сайт открывается только после readiness-проверки. Если запуск задержался, сохраняется экран «Запуск после технических работ занимает больше времени. Попробуйте обновить страницу позже», повторная проверка и уведомление владельцу; приложение не обещает недостоверную готовность. Status/maintenance не должны кешироваться на весь следующий день.

### Согласованный технический цикл

| Время МСК | Действие |
|---|---|
| 23:55 | Предупреждение методисту о закрытии; показать неподтверждённые сохранения и дать завершить правки |
| 00:00 | Закрыть новые операции серверным gate, включить ночной UI; дождаться завершения уже принятых операций в ограниченном окне до 2 минут |
| После завершения операций | Отправить асинхронный stop и подтвердить STOPPED; при неуспехе повторить безопасно и уведомить владельца |
| 07:45 — согласовано | Начать запуск БД, проверить RUNNING, SQL-readiness и доступность опубликованного контента. Пользовательский UI остаётся закрыт до 08:00 |
| 08:00 | Открыть доступ только при готовности всех зависимостей; иначе показать продление работ и отправить алерт |

**Разница с буквальной остановкой 00:00–08:00:** остановка асинхронна и требует завершения операций, а прогрев означает работу БД последние 15 минут ночного окна. Пользовательское окно остаётся строго 00:00–08:00. 31 августа 2026 года владелец подтвердил начало запуска БД в 07:45 МСК при сохранении ночного экрана до 08:00. Это разрешённое техническое окно прогрева; таймер ещё не развёрнут. Достаточность 15 минут подтвердить несколькими тестовыми циклами, не считать её гарантией готовности.

Уже принятые до полуночи записи либо подтверждаются после commit, либо явно возвращают ошибку; не показывать «Сохранено» заранее. Неподтверждённые изменения админки остаются в памяти вкладки с предупреждением до возобновления работы — без скрытого сохранения в браузерное постоянное хранилище. Ночная остановка не должна добавлять хранение ответов читателя.

### Исполнение расписания

Cloud Functions с IAM-защищённым вызовом и таймерами Yandex Cloud; это часть инфраструктуры, не локальное напоминание на компьютере. Отдельный controller identity имеет минимально доступные сервису права в изолированном каталоге; код дополнительно ограничен точным cluster ID «Прожито», не выбирает цель из HTTP-параметров. Не выдавать ему права на FinPulse и payload пользовательских секретов.

Помимо суточных событий — сверка каждые 5 минут: controller вычисляет желаемое состояние по текущему серверному времени и сравнивает с Cloud API. Повторные/запоздавшие события не должны запускать БД ночью или останавливать утром. Для STARTING / STOPPING / UPDATING не отправлять противоположную операцию; сохранять/проверять operation ID и повторять сверку после завершения. Ошибки запуска/остановки имеют ограниченные retries, backoff и алерт. Пропущенный start должен восстанавливаться без ручного открытия публичной start-ссылки.

Время таймеров Cloud Functions задаётся в UTC: 00:00 МСК соответствует 21:00 UTC предыдущего календарного дня, 07:45 — 04:45 UTC, 08:00 — 05:00 UTC. Генерировать настройки из единого контракта расписания; ручные несовпадающие часы frontend/backend/controller недопустимы. [Формат таймеров](https://yandex.cloud/ru/docs/functions/concepts/trigger/timer).

Перед первым stop обязательно создать и проверить backup: сервис не позволяет остановить кластер без резервной копии. Планировать backup и обслуживание внутри времени работы БД с достаточным запасом до полуночи; не копировать ночное backup-окно из постоянно работающего контура. Если backup/обслуживание ещё не закончились, не форсировать остановку: продлить работу БД при закрытом UI, дождаться завершения и зафиксировать дополнительный расход. Отдельно проверить покрытие PITR последними дневными записями. [Остановка кластера](https://yandex.cloud/ru/docs/managed-postgresql/operations/cluster-stop).

Критерии приёмки реализации: 23:59 → 00:00 и 07:59 → 08:00; часы устройства в другом часовом поясе; переход календарной даты UTC; уже открытая/уснувшая вкладка; остановленная БД при открытии сайта; сохранение перед полуночью; замедленный start; неуспешный stop; дубли и пропущенные события; кешированный maintenance; существование backup и восстановление; отсутствие прав на FinPulse. Эти runtime-проверки ещё не выполнялись.

## 8. Развёртывание и откат

После согласования:

1. Terraform описывает только новые ресурсы «Прожито»; существующий FinPulse не импортируется в его state и не изменяется. Раздельный закрытый state окружений, versioning, контролируемая сериализация apply; секретные payload в Git и state не складывать.
2. Pull request запускает typecheck, тесты контракта, API/редактора, сборки и интеграцию с изолированной PostgreSQL. Никаких production-данных в CI.
3. GitHub OIDC → Yandex WIF выдаёт короткоживущий доступ с привязкой к конкретному repo и защищённой ветке/environment. Отдельное подтверждение production deployment. [WIF с GitHub](https://yandex.cloud/ru/docs/iam/tutorials/wlif-github-integration).
4. Версионированные миграции запускаются отдельной служебной задачей внутри VPC с migration identity и ledger/lock, не при старте каждого runtime. Вариант реализации — отдельный непубличный migration container с ограниченным IAM-вызовом; его connectivity и timeout проверяются на staging. GitHub-hosted runner не получает публичный порт БД ради миграций.
5. Затем выкладываются совместимая ревизия API и статические сборки. Immutable assets загружаются до нового index/manifest; предыдущий комплект сохраняется. API и frontend допускают короткий период разных версий.
6. Smoke: health отдельно от readiness БД; публичный контент; неавторизованный admin → 401; запрет анонимного вызова container URL; редакторский preview/publish/rollback; сохранность контента после повторного deploy.
7. Откат кода — предыдущий образ и статический manifest. Откат публикации — предыдущая редакция контента. Откат схемы — отдельный план, не автоматический destructive down; применять совместимые expand/contract-миграции.

| 3. Админка | Черновик → preview → согласование → publish → rollback | Методист меняет материал без разработчика; конфликт правок не теряет данные; читатель видит только опубликованное |
| 4. Подключение reader и cutover | API вместо build-time Markdown для рабочего приложения | Полный QA всех 22 Section и трёх упражнений, экспорта книги, иллюстраций; backup restore и rollback проверены |
| 5. Редакторский вход | Отдельная админка; пароль + TOTP; защищённая сессия | Разграничение, CSRF, ограничения попыток и отзыв сессии проверены; аккаунты читателей исключены |

Существующий GitHub Pages остаётся отдельной демонстрационной версией и в задаче внедрения не изменяется. Развёртывание нового контура разрешено владельцем; оно не разрешает публикацию несвязанных накопленных правок. Ночную блокировку не включать в нынешнем полностью статическом демо: она не экономит отсутствующую БД. Расписание и maintenance активируются совместно при подключении нового DB-backed контура. Если оставить Pages после cutover, явно указать дату/статус демо, чтобы оно не считалось синхронным рабочим источником.

## 10. Согласованные параметры и оставшееся уточнение

Все исходные вопросы закрыты: денежного лимита пока нет; нужна отдельная админка с редакторским входом, сайт открыт без аккаунтов и прогресса; это веб-пилот примерно на 100 посетителей в день; разрешён существующий домен облака; создан новый каталог. Ночное окно и прогрев с 07:45 МСК сохраняются.

Первый редактор `editor` создан с уникальным случайным паролем и TOTP. Пароль и ключ аутентификатора находятся в Lockbox; значения не пишутся в переписку, репозиторий или команды. Runtime получает только пароль своего пользователя БД и секреты MFA/ограничения попыток; пароль редактора ему не передаётся. В БД хранится scrypt-хеш. Публичная регистрация не предусмотрена.

Фактически созданы PostgreSQL 17 `s3-c2-m8`, один закрытый хост / 10 GiB network SSD / 14 дней копий, приватный API, три закрытых бакета, два HTTPS-шлюза, Lockbox, таймер и контроллер. Контроллер имеет права только на конкретный кластер, не весь каталог; каждые пять минут сверяет время МСК. После полуночи есть drain: первое штатное выключение — около 00:05, запуск — 07:45, открытие — не раньше 08:00 и готовности БД. Созданы только новые DNS-записи `prozhito.ncfg.ru` / `prozhito-editor.ncfg.ru` и их ACME-проверки. FinPulse, существующие DNS-записи и GitHub Pages не менялись.

Граница первого редактора: текст, девять звеньев, вопросы/пояснения трёх существующих упражнений, выбор уже импортированных изображений и alt; черновик, настоящий reader-preview, публикация и откат всей публикации. Загрузка новых медиа и разделение ролей нескольких сотрудников пока не реализованы. Первоначальные рекомендации о signed upload, трёх ролях и CI/Terraform выше — дальнейшие пункты, а не описание готовых возможностей. Канонические Markdown не перезаписываются из БД автоматически; полный методический release-pass и организационный cutover не объявлялись.
