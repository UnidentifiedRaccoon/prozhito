# Дизайн-система статической демоверсии

## Область действия

Документ определяет визуальные и технические договорённости только для статической React-демоверсии «Прожито». Он не выбирает UI-архитектуру будущего полного Reader и не меняет продуктовую модель, структуру `6 / 22` или контракт двух экранов Section.

Дизайн-система растёт из фактических потребностей приложения. Новый компонент, вариант или токен добавляется вместе с конкретным использованием и отдельной story; каталог внешней библиотеки не переносится целиком.

## Визуальный язык `living_archive_v1`

Утверждённое направление называется «Живой архив». Интерфейс соединяет современную редакционную типографику с материальностью бумажного архива: тёплая хлопковая бумага, графитовый текст, тонкие линейки и прозрачная акварель. Система не имитирует музей, старую рукопись или ретро-приложение; она остаётся ясной современной оболочкой для длинного чтения.

Основные правила:

- viewport использует спокойный canvas `#ebe5da`, контент — непрерывную paper surface `#f7f3ea`;
- на desktop приложение выглядит как одна длинная paper sheet с hairline, мягкой тенью и радиусом; на mobile поверхность идёт от края до края без рамки устройства;
- основной текст — graphite `#2f302d`, вторичный — `#65665f`, функциональный accent/focus — blue ink `#315f76`;
- mist blue, ochre, sage и dusty mauve применяются только в иллюстрациях, washes и декоративных маркерах; ими нельзя набирать основной текст или кнопки;
- литературный serif stack обслуживает заголовки и чтение, system sans — управляющий текст, labels и номера;
- иллюстрации остаются лёгкими и растворяются в paper surface; глянцевые карточки, тяжёлые тени, sepia-grunge и декоративная «старина» запрещены;
- сгенерированный raster не хранит пользовательские labels, даты, суммы и UI. Проверяемый текст остаётся HTML/Markdown;
- концептуальные иконки не становятся интерфейсными кнопками без реального действия.

Саша канонически закреплена как женщина, а выбранный D-F «Наблюдательная ирония» хранится как исходный character anchor. Сюжетные продолжения генерируются от этого anchor и `living_archive_v1`, а не от последней сцены, чтобы не накапливать дрейф лица и одежды.

## Принципы

1. Контент и читаемость важнее декоративной механики.
2. Публичный API компонента выражает конечные продуктовые варианты через типизированные props.
3. Компонент получает один базовый класс и отдельные классы размера, варианта или тона через `cn()`.
4. Стили компонента хранятся рядом с ним в CSS Module; глобальный CSS содержит только токены, базовые элементы и существующие экранные стили.
5. CSS custom properties используются для общих токенов и значений, меняющихся между вариантами. Постоянная структура компонента записывается обычными CSS-свойствами.
6. `data-*` не является собственным API стилизации. Атрибуты состояния, которые создаёт Base UI, могут оставаться в DOM; при необходимости визуальное состояние преобразуется в семантический CSS-класс без дублирования React-state.
7. shadcn/ui используется как справочник по структуре, состояниям, доступности и edge cases. Его runtime, CLI-код и Tailwind-оформление не являются зависимостью проекта.
8. Base UI подключается как headless-основа. Нативный HTML остаётся предпочтительным для простой семантики; сложное поведение не реализуется заново вручную.
9. Навигация остаётся нативной ссылкой, даже когда визуально совпадает с кнопкой. Публичный `Button` выбирает семантическую ветку по `href`: `<a>` для перехода и Base UI Button для действия.

## Слои токенов

Токены находятся в `src/styles/tokens.css` и образуют три небольших слоя:

1. **Primitive** — исходные цвета, интервалы, шрифты, форма и motion.
2. **Semantic** — назначение в приложении: `--text`, `--muted`, `--accent`, `--border`, `--focus`.
3. **Component-local** — переменные внутри CSS Module, например `--button-height` и `--button-background`.

Компонент обращается к semantic token, а не к сырому цвету. Component-local token добавляется только тогда, когда одно значение действительно меняется между вариантами или размерами.

Dark mode не входит в текущий scope. При его появлении меняется semantic-слой, а не CSS компонентов.

Акварельные primitive tokens являются декоративными. Компонент может выбрать их для wash или marker, но смысл и состояние всегда передаются текстом, структурой и доступным функциональным цветом.

## AppShell и каталог

`AppShell` создаёт единую paper sheet и тихий masthead. На каталоге `Прожито` является единственным компактным `h1`; на внутренних экранах тот же wordmark становится реальной ссылкой к каталогу. Большой повторный product title не выводится, а декоративные элементы masthead не имитируют controls.

Каталог сохраняет один программный порядок `6 / 22`:

- Roman numeral обозначает только уровень;
- двухзначный Arabic number обозначает Section внутри уровня;
- каждый уровень имеет отдельный разделительный visual band;
- каждый из шести уровней использует catalog crop сюжетного master своей первой Section; отдельная генерация для каталога не создаётся;
- первый catalog crop загружается eagerly с высоким приоритетом, остальные не preload-ятся и используют lazy loading;
- Section остаются простыми ruled rows, а не карточной сеткой.

## CSS и TypeScript

Рекомендуемая структура компонента:

```text
Component/
├── Component.tsx
├── Component.module.css
└── Component.stories.tsx
```

Варианты связываются с классами исчерпывающей map:

```ts
const componentSize = {
  small: styles.sizeSmall,
  medium: styles.sizeMedium,
  large: styles.sizeLarge,
} satisfies Record<ComponentSize, string>;
```

`satisfies Record<...>` блокирует тихое расхождение union-типа и CSS-вариантов. `cn()` является тонкой обёрткой над `clsx`; `tailwind-merge` не используется.

Внешний `className` допустим для положения компонента в layout, но не должен создавать новые скрытые варианты дизайна. Повторяющееся переопределение означает, что нужно обсудить новый prop или отдельный компонент.

## Button

### Назначение

`Button` задаёт единое визуальное семейство заметных действий и переходов. При наличии `href` он рендерит нативный `<a>` напрямую; без `href` — Base UI Button. Base UI Button не используется для имитации ссылки.

### API

- `variant`: `filled | outline | ghost`;
- `size`: `small | medium | large`;
- `href` отсутствует — доступны разрешённые props Base UI Button, `type` по умолчанию равен `button`;
- `href` задан — доступны нативные anchor props и рендерится `<a>`;
- `disabled` существует только у button-ветки; недоступная навигация не маскируется disabled-ссылкой;
- `render`, `nativeButton` и `focusableWhenDisabled` не входят в публичный контракт.

### Состояния

- default, hover, active, keyboard focus;
- disabled;
- reduced motion и forced colors.

Loading, icon-only и danger tone не входят в текущий контракт и не добавляются без фактической потребности.

## Text

### Назначение

`Text` задаёт повторяемую визуальную роль текста, не подменяя HTML-семантику.

### API

- `variant`: `body | lead | label | caption`;
- `tone`: `default | muted | accent`;
- `as`: `p | span | div | strong | em | small`.

Заголовки не входят в `Text`. В приложении `Text` используется для вводного текста каталога, подписей продуктовых компонентов и сообщений; текст истории остаётся непрерывным Markdown-контентом.

## Heading

### Назначение

`Heading` задаёт утверждённые типографические роли заголовков и не связывает визуальный размер с HTML-уровнем.

### API

- `as`: `h1 | h2` — обязательная семантика из текущих экранных сценариев;
- `variant`: `display | page | section` — обязательная визуальная роль;
- `display` используется для названия продукта, `page` — для единственного `h1` экрана, `section` — для заголовка уровня каталога.

Новые уровни и варианты не добавляются заранее. Заголовки внутри сложного продуктового компонента могут оставаться локальными, если их типографика является частью его собственной анатомии — как labels в `DecisionChain`.

## SectionHeader

`SectionHeader` — продуктовая шапка двух экранов Section. Она объединяет один `Heading as="h1" variant="page"` и типизированную подпись `История | Решение`, отделяет шапку от контента и сохраняет одинаковую вертикальную структуру обоих экранов.

Компонент не принимает произвольные children и не используется для каталога или системных сообщений.

## SectionHeroHeader

`SectionHeroHeader` из `src/components/product` — общая immersive-шапка двух экранов Section с проверенными assets. Типизированный `variant: story | analysis` не является свободным визуальным переключателем: каждое значение фиксирует пользовательскую подпись, aria-label навигации, высоту, crop и локальную graphite-вуаль. В обоих случаях единственный `h1` и подпись остаются настоящим HTML, а не частью raster.

Вариант `story` сохраняет утверждённую «Акварельную обложку» и более высокую сюжетную композицию. Вариант `analysis` использует отдельный hero-safe предметный still-life и компактную высоту: он визуально связывает два экрана, но не откладывает начало девятизвенной цепочки на ещё один полный viewport. Для всех 22 Section обязательный сюжетный субъект или предметы сгруппированы в центральной mobile-safe зоне, а нижняя часть raster оставлена свободной под заголовок. Нижний `SectionArtwork` перед footer на экране «Решение» не дублируется.

`variant` продолжает задавать только семантику, высоту, copy и hero-анатомию. Индивидуальные desktop/mobile focal positions хранятся типизированными metadata рядом с asset в `src/visuals/sectionVisuals.ts` и передаются в CSS custom properties; CSS не содержит условий по Section ID. Forced-colors поведение hero сохраняется.

В hero существует ровно один navigation control: нативная круглая ссылка 44 × 44 px со стрелкой влево, всегда ведущая в общий каталог. Видимого текста у control нет; доступное имя — `Все истории`. Burger-icon не используется, потому что отдельного меню hero не открывает. Сюжетное изображение сохраняет смысловой alt; декоративный still-life использует пустой alt. Оба raster не принимают pointer events, не выделяются и не перетаскиваются.

Storybook сохраняет прежний story-id `cover-overlay` для сюжетной композиции и отдельную story экрана «Решение». Отклонённые `archiveLabel`, `imageThenTitle`, scroll cue и их CSS не возвращаются. Raster не содержит текста, дат, сумм, логотипов или UI; контраст создаётся CSS. Все 22 Section имеют проверенную пару assets. Любой будущий asset требует отдельной проверки crop и контраста на mobile/desktop.

## SectionFooter

`SectionFooter` — продуктовая нижняя навигация Section. Он рендерит семантические `footer` и `nav`, затем две link-ветки `Button`:

- опциональное вторичное ghost-действие возвращает к списку;
- filled-действие ведёт к экрану «Решение», следующей истории или возвращает к списку после последней Section.

Все действия остаются нативными `<a>`; компонент не превращает навигацию в button-action и не вычисляет маршруты самостоятельно. На последнем экране «Решение» вторичная ссылка не передаётся, потому что основное действие уже ведёт к тому же каталогу.

## Контент истории

История отображается как обычный непрерывный текст. `react-markdown` остаётся техническим адаптером канонических Markdown-файлов и не создаёт отдельную визуальную сущность `Prose`.

Если для Section существует проверенный story asset, `SectionArtwork` может стоять между `SectionHeader` и непрерывным Markdown. Иллюстрация не сокращает фрагмент, не делит его на карточки, не добавляет событие и не содержит отдельный CTA.

Новый content block добавляется только при появлении отдельной семантики, например цитаты, примечания или предупреждения. Простое отличие в отступе или цвете не является достаточной причиной для нового блока.

## DecisionChain

`DecisionChain` отображает ровно девять канонических звеньев разбора решения в фиксированном порядке. Утверждён единый дизайн `Path`: смысловые поверхности соединены вертикальной линией и ромбовидными маркерами.

- компонент получает типизированный массив `AnalysisItem[]` из content parser;
- видимая нумерация отсутствует, но DOM сохраняет семантический `<ol>`;
- `variant` отсутствует: экспериментальные `Thread` и `Axis` удалены после выбора;
- линия и маркеры декоративны и скрыты от accessibility tree;
- компонент проверяет число и порядок labels до рендера.

В `living_archive_v1` items являются открытыми текстовыми блоками без card surface. Акварельные цвета маркеров циклические и строго декоративные: они не кодируют категории, риск, статус или прогресс. В forced colors маркеры и rail переходят на системные цвета.

## SectionArtwork

`SectionArtwork` — адаптивная рамка для project-bound raster assets, подключаемых по `section.id` отдельно от Markdown и parser.

- `variant`: `catalog | story | analysis`;
- source, размеры и alt-текст приходят из `src/visuals/sectionVisuals.ts`;
- `story` использует master `3:2`, на узком экране — crop `4:3`;
- `catalog` использует crop того же master, а не отдельную генерацию персонажа;
- `analysis` хранит отдельный предметный still-life и используется через `SectionHeroHeader`, не дублируясь после девятого звена;
- mobile и desktop focal positions хранятся рядом с asset metadata и не создают новые visual variants;
- смысловой asset получает точный alt, полностью дублирующий текст декоративный asset — пустой alt;
- приложение никогда не ссылается на `$CODEX_HOME/generated_images`: финальные файлы хранятся внутри workspace.

В `src/assets/living-archive` для каждой Section сохраняются generation master `1536 × 1024` и отдельный оптимизированный runtime export `1200 × 800`. Приложение импортирует runtime exports и повторяемую `paper-canvas-512.jpg`; masters и D-F anchor остаются project references и не входят в runtime bundle.

## Storybook

Storybook является локальной мастерской и документацией компонентов. Он не публикуется и не подключается к внешнему visual-regression сервису.

Каждый компонент должен иметь:

- интерактивный Playground;
- stories всех утверждённых вариантов и размеров;
- semantic/disabled states, если они существуют;
- краткое описание назначения и ограничения в autodocs;
- accessibility-проверку через addon-a11y.

`SectionArtwork` документирован отдельными stories для `story`, `catalog` и `analysis`.

Storybook импортирует тот же `src/styles.css`, что и приложение. Телеметрия и уведомления Storybook отключены.

## Управление изменениями

При изменении компонента одновременно проверяются:

1. публичные TypeScript-типы;
2. CSS Module и токены;
3. stories и autodocs;
4. keyboard focus и контраст;
5. существующие экраны приложения.

Не начинать следующий компонент автоматически. Сначала должен появиться конкретный пользовательский или экранный сценарий.
